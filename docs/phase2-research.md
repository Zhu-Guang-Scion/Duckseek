## 1. 多候选 SQL + 选择器 —— **建议优先级 1（M7-B）**

**问题定义**：V5-D 已实证 temperature=0 下单次生成仍非确定（摆动清单
#7/#11/#16/#19 双向翻转）——边界问句的质量取决于「抽中哪一次」。

**方案空间**：
- (a) **执行一致性选择器**（推荐）：N 路并行生成（同温 0，靠模型固有
  非确定性；或 temperature 0.3 增益离散度）→ 逐路 guard → 全部执行 →
  **结果多重集合多数决**（eval runner 已实现的 L3 多数决逻辑可直接复用
  为运行时选择器）；无多数时取「护栏通过且执行成功」中首个并如实标注
  `candidates_disagree`。
- (b) LLM 裁判：多一次调用对比候选 SQL——引入新失败面，且裁判本身不稳定，不推荐。
- (c) 仅在失败时升级多候选（retry 时并行 3 发）：成本最低，但只救执行
  失败，救不了「错而能执行」的语义摇摆。

**成本模型**（据 E1）：N=3 全量 ≈ 3× 生成 token（~14K/问）；(c) 方案仅对
3.4% 重试问句付费。延迟：并行调用墙钟≈单次。

**与现架构接点**：改动集中在 `nl2data/qa.py`（ask_once 内候选循环）与
`eval/e2e.py`（多数决函数抽公共）；**评估优势**：现成三层 runner 可直接
A/B（基线 0.75/带内 [0.75,0.80] vs 多候选），完全符合「敢迭代」纪律。

**风险**：token 成本 ×3（个人规模可接受）；「错而一致」型错误多数决救不了。

## 2. 实体索引 —— **建议优先级 2（M7-A），且 v1 有廉价形态**

**问题定义**：问句里的数据值（行政区中文名、机场 zone 名、支付码）需要
精确落进 SQL 字面量；当前靠模型自身知识翻译（曼哈顿→'Manhattan'）与
5 个样本值碰运气。联调副产品已实证：跨语言实体 4/6 命中、borough 类
生僻词无字面抓手。

**证据（E2）**：缺口集中在 (i) taxi_zones.zone 261 值不在卡片；(ii) 中文
→英文名映射无任何系统支撑；(iii) pulocationid 类编码列靠 JOIN 规避（现状已 OK）。

**方案空间**：
- (a) **小维度表全量值注入（推荐 v1）**：行数 ≤500 的维度表（本例
  taxi_zones 恰 265 行）在卡片里注入全量「编码→名称」清单（zone+borough
  约 2.6K 字符 ≈ 700 token，在 2000 token 预算内单列一块）；跨语言由
  glossary synonyms 承接（「曼哈顿→Manhattan」类词条）。改动面：
  cards 装配 + token 预算打包，无新索引设施。
- (b) 通用值索引：高频字符串列 distinct 值入 LanceDB（与表卡片同构），
  检索命中后作为「值提示」注入提示词。覆盖任意大表，但需新增索引对象
  与嵌入成本——建议作为 (a) 不够用后的 2.5 期形态。
- (c) 只扩 sample_values 数量：最便宜但无编码→名称映射语义，不解决跨语言。

**评估**：golden #5/#8/#13/#15/#17（行政区/机场类）即靶点；A/B 用现成 runner。

## 3. 查询缓存 —— **建议优先级 3（小而独立，或并入 M7 任一项）**

**证据（E3）**：拆分流量后真实交互命中率 22%（6/27）、全周期省 ~2.7 万
token、~6 次×(5-13s) 延迟——**成本收益在个人规模下均边缘**。直觉中的
「93% 命中率」几乎全部来自 eval 回放，而 eval 恰恰必须绕过缓存。

**若仍要做**（形态已成熟，半天量级）：sha256 磁盘缓存（复用 embedding
cache 模式）；键=规范化问句 + catalog ingested_at 指纹（数据变更自动失效）；
值=完整载荷（sql/answer/统计）；**eval 与 --force 显式绕过**；命中响应标注
`cache_hit: true`（披露纪律与 embedding_degraded 同型）。

## 4. Python 分析沙箱 —— **建议降级/除名（需人类裁定，涉 §4 清单变更）**

诚实评估：
- **安全面**：把「SQL-only 双防线」升级为「任意代码执行」是质的恶化。
  RestrictedPython 不是安全边界；subprocess 隔离在 Windows 上形同虚设；
  WASM/pyodide 引入量级依赖。个人单机工具为此付出的是**架构级**代价。
- **需求面**：golden 20 问与至今全部真实用法（619 审计事件）中没有一例
  需要 SQL 之外的计算能力（分位数/占比/加权平均 DuckDB 全覆盖）。
- **替代路径**：若未来确需复杂后处理，「表达式白名单」（duckdb SQL 宏 +
  过审 Python UDF 清单）是不破坏安全模型的中间态。

**建议**：从阶段二清单移除或降级为「阶段三按需评估」；释放的精力投向
方向 1/2。此为 §4 变更，需人类批准。
